Phase 2 — Web login and device authorization

The browser approves the device. Credentials return only through the plugin polling channel.

Onboarding sequence

1. Plugin

Request device authorization

→

2. API

Issue a 10-minute device code

→

3. Browser

Login and approve the named device

→

4. Plugin

Poll the approved code and register

Web Admin session

Password: Argon2id hash in a dedicated credential row, never on the identity row.

Session: opaque random ID; only its hash is stored server-side.

Cookie: Secure, HttpOnly, SameSite=Lax, bounded idle and absolute expiry.

CSRF: origin check plus per-session token for state-changing forms.

TOTP: optional enrollment and recovery codes; secret encrypted at rest.

Obsidian device credential

Access token: opaque, workspace/device scoped, 15-minute lifetime.

Refresh credential: rotating family with 30-day inactivity and 90-day absolute expiry.

Storage: Obsidian SecretStorage; plugin data stores only the secret name.

Reuse detection: reuse of a rotated token revokes the device family.

Admin revoke: immediately disables access and pending grants.

Minimal Web Admin surface

Login

Password, optional TOTP and rate-limit feedback

Device approval

Name, platform, requested sync scope and expiry

Devices

Status, registered/last-seen time and revoke

Exclusions

Draft, preview impact, publish revision and audit

Security invariants

  • No token in a browser URL, redirect history or plugin settings JSON.
  • Every credential derives user, workspace and device scope server-side.
  • Login, approval, refresh, revoke and policy publication are safely audited.
  • Disabled user, revoked device or expired grant fails closed.

Deliberately deferred

  • Passkeys/WebAuthn.
  • External OIDC providers.
  • Multi-user roles and collaboration.
  • Token delivery through custom URI callbacks.
